# Sell safe change, not another agent

Ritru Labs should not build its own AI agent. The cloud vendors and security vendors already give agents away for free, bundle them into products, or have hundreds of millions of dollars to build them. What Ritru should sell is the safe "last mile" around those agents. That means three things. First, an agent that turns security findings into small code fixes delivered as pull requests. Second, a fixed-price review that gets stalled agent pilots ready for production. Third, a narrower version of the landing zone agent that the founder already evaluated. This version upgrades and checks existing landing zones and leads with the forced Azure move from the old CAF Terraform module to Azure Verified Modules. It does not generate new multi-cloud landing zones from scratch. The evidence is consistent across sources. Only about **17–23% of organisations run agents in production** ([Joget summary of Gartner](https://joget.com/ai-agent-adoption-in-2026-what-the-analysts-data-shows/); [McKinsey](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai)). **More than 40% of agentic projects are expected to be cancelled by the end of 2027** ([Gartner](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)). The top blockers are data access, identity and security controls, and monitoring, not model quality ([KPMG Q3 2026](https://kpmg.com/kpmg-us/content/dam/kpmg/corporate-communications/pdf/2026/AIPulseSurvey_Q3_FINAL.pdf)). Buyers trust agents that read, suggest and open a pull request for a human to merge. They do not trust agents that change production on their own. All three first offers can run on one shared "change engine", the PR-based design already drafted in Ritru's Jira-to-PR blueprint. A small team can therefore build once and sell three ways. The commercial ladder is simple: free open blueprints, then a fixed-fee review, then a fixed-fee pilot, then a production build, then a monthly run fee, with a small optional bonus tied to measured results.

**Words used in this report**

| Term | Plain meaning |
|---|---|
| Agent | AI software that plans steps and uses tools (reads logs, edits code) to finish a task, not just answer a question |
| Pull request (PR) | A proposed code change that a named human must review and approve before it is used |
| Infrastructure as code (IaC) | Cloud setup written as code files (Terraform, Bicep, CDK) instead of clicked together in a console |
| Landing zone | The base setup of a cloud estate: accounts, networks, identity, logging and guardrails that every workload sits on |
| Drift | When the live cloud no longer matches what the code says it should be |
| Plan | A dry run that shows exactly what a change would create, modify or delete, without doing it |
| Policy check | An automatic rule test on the plan, for example "no public storage buckets" |
| MCP | A common plug standard that lets an agent connect to a tool, such as a cloud API or a ticket system |
| Least privilege | Giving the agent only the narrowest access it needs, for the shortest time |
| SOC | Security operations centre: the team that reviews security alerts |
| MTTR | Mean time to resolve: how long incidents take to fix, on average |
| Shadow mode | The agent runs and makes suggestions, but humans still do the real work, so you can compare its answers to theirs |
| Evidence bundle | The saved record of a change: why it was made, the plan, the policy results, who approved it and what was applied |

## Only one firm in five runs agents for real, and they buy bounded ones

Headline adoption figures depend on who is asked. Independent analysts put real deployment low. **Gartner's 2026 CIO survey says 17% have deployed agents**, and **McKinsey says 23% are scaling an agentic system** ([Joget summary of Gartner](https://joget.com/ai-agent-adoption-in-2026-what-the-analysts-data-shows/); [McKinsey](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai)). Surveys of very large firms report about half "deployed". KPMG's US $1B+ sample sat flat at 53–55% in Q2 2026 ([KPMG Q2 2026](https://kpmg.com/us/en/media/news/q2-ai-pulse-2026.html)). These samples skew to big companies and count loosely. The honest message for Ritru's clients is that most of their peers are still piloting. Where agents do scale, IT, IT service management and software engineering go first ([McKinsey](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai)). In Gartner's survey of 782 infrastructure and operations leaders, **gen AI in IT service management made up 53% of all reported AI successes** ([Gartner, April 2026](https://www.gartner.com/en/newsroom/press-releases/2026-04-07-gartner-says-artificial-intelligence-projects-in-infrastructure-and-operations-stall-ahead-of-meaningful-roi-returns)).

Returns show up where the work is bounded, frequent and easy to check. Code migration has the best evidence. Google's study of 39 internal migrations found that roughly 70% of edits were written by an LLM. Developers estimated a 50% time saving, which is an estimate rather than a measurement ([arXiv 2504.09691](https://arxiv.org/pdf/2504.09691)). Incident triage shows real but modest gains. A credible figure to quote to clients is **10–45% faster mitigation on supported incident types**, not the 50–70% that vendors advertise. One evaluation guide puts the average MTTR cut at 17.8% ([Augment Code](https://www.augmentcode.com/tools/ai-incident-management-software)). The failures cluster in one place: open-ended, autonomous action. In Gartner's operations survey, **only 28% of AI use cases fully met their ROI goals and 20% failed outright**. Gartner named auto-remediation and "self-healing" infrastructure as tasks AI is not yet ready for ([The Register](https://www.theregister.com/software/2026/04/07/only-28-of-ai-infrastructure-projects-fully-pay-off/5221652)).

What stops firms now is plumbing and control, not the AI model. KPMG's Q3 2026 survey lists the top barriers as **data access (59%), security and identity controls (53%), monitoring of AI outputs (47%) and policy enforcement (42%)** ([KPMG Q3 2026](https://kpmg.com/kpmg-us/content/dam/kpmg/corporate-communications/pdf/2026/AIPulseSurvey_Q3_FINAL.pdf)). Gartner found that 74% of IT application leaders see agents as a new attack route, and only 13% strongly agree they have the right governance ([Gartner, September 2025](https://www.gartner.com/en/newsroom/press-releases/2025-09-30-gartner-survey-finds-just-15-percent-of-it-application-leaders-are-considering-piloting-or-deploying-fully-autonomous-ai-agents)). IBM found that **97% of organisations whose AI was breached lacked proper AI access controls** ([VentureBeat on IBM](https://venturebeat.com/business/ibm-shadow-ai-breaches-cost-670k-more-97-of-firms-lack-controls)). Each of these is a services problem. None is fixed by buying one more agent.

Buying habits point the same way. Enterprises **bought 76% of their AI solutions in 2025, up from 53% in 2024**, and bought tools reached production 47% of the time ([Menlo Ventures](https://menlovc.com/perspective/2025-the-state-of-generative-ai-in-the-enterprise/)). Most firms still expect to customise what they buy. Deloitte puts that at 85% ([Libertify summary of Deloitte](https://www.libertify.com/interactive-library/state-of-ai-enterprise-2026-deloitte-survey/)). The buyer is spread out. One modest survey has the CEO named in 49% of AI sign-offs and finance in 31% ([Open Future Forum](https://openfutureforum.com/research/executive-ai-leverage-report-october-2026)). The CISO, CIO, CTO and data chief all touch agent governance ([Cybersecurity Insiders](https://www.cybersecurity-insiders.com/ai-governance-ciso-authority-gap/)). In practice, every Ritru proposal needs two things: a return-on-investment baseline a finance chief can read, and a controls story a CISO will accept. Outcome-based contracts are growing but still a minority. Gartner says **only 13–19% of services deals use them today** ([Channel Dive](https://www.channeldive.com/news/agentic-ai-outcome-pricing-models-zendesk-gartner/829209/)). Even so, Accenture now books **65% of its work as fixed-price or outcome-based** ([BusinessToday](https://www.businesstoday.in/amp/markets/stocks/story/tcs-infosys-hcl-tech-wipro-techm-3-takeaways-from-accentures-q4-results-top-picks-559576-2026-10-05)). Fixed-price packages are the norm Ritru must match.

## The real gaps sit where vendor agents stop

The openings all share one shape. A vendor agent does its job well inside its own product and then stops at the edge. Six edges matter for Ritru.

The first edge is the client's own code. Cloud security tools find problems in the running cloud. The fix has to land in the Terraform or Bicep module that created the resource, or the next deploy will undo it. Wiz's own agent has to gather "ownership data and past fixes" before it can plan a fix ([Wiz](https://wiz.io/blog/securing-software-age-of-agentic-coding)). That context lives in each client's repositories and CI rules, which is why this is integration work. The second edge is existing estates. Microsoft's migration tooling from the old CAF module to AVM covers **only resources the classic module could deploy**. Custom resources need manual handling ([Microsoft](https://techcommunity.microsoft.com/blog/azuretoolsblog/terraform-azure-verified-modules-for-platform-landing-zone-alz-migration-guidanc/4432035)). The third edge is honest measurement. Vendors claim more than 95% accuracy for root-cause analysis, and CrowdStrike claims more than 98% for alert triage ([Komodor](https://komodor.com/blog/komodor-ai-sre-vs-oss-ai-agent-a-technical-comparison-of-agentic-ai-for-kubernetes-troubleshooting/); [CrowdStrike](https://www.crowdstrike.com/en-us/press-releases/crowdstrike-unleashes-agentic-security-workforce-to-transform-security-operations)). Independent benchmarks tell a different story. The best models recover the exact root cause in **about 21% of cases** on OpenRCA 2.0 ([emergentmind](https://www.emergentmind.com/papers/2606.27154)). They make up implausible root causes in 7–40% of reports on ORCA-bench ([alphaxiv](https://www.alphaxiv.org/abs/2607.28545.md)). One October 2026 study found a triage design that looked efficient because it escalated few alerts, but it **quietly dismissed 54.2% of real attack alerts** ([arXiv 2610.10608](https://arxiv.org/html/2610.10608)). Gartner's warning fits: of the large SOCs that pilot agents, only 15% will see measurable gains without a structured evaluation ([Help Net Security](https://www.helpnetsecurity.com/2026/09/09/prophet-security-evaluating-ai-soc-agents/)).

The fourth edge is governance of the agents themselves. Azure SRE Agent's approval gate covers only Azure infrastructure operations. Emails, Teams posts and outside data queries "proceed based on the agent's reasoning" ([Microsoft Learn](https://learn.microsoft.com/azure/sre-agent/run-modes)). GitHub's agent firewall does not cover MCP servers ([GitHub docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). The attack record is real. A malicious public GitHub issue tricked an agent into leaking private repository data ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). Poisoned Nx packages ran local AI command-line tools with their safety prompts switched off, and leaked over 20,000 files ([Wiz](https://wiz.io/blog/s1ngularitys-aftermath)). An agent with production access deleted a live database during a code freeze ([eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)). The OWASP Top 10 for Agentic Applications, published December 2025, gives a shared checklist for these risks ([Teleport](https://goteleport.com/blog/owasp-top-10-agentic-applications/)). The fifth edge is cost, covered above. The sixth edge is self-hosted toolchains. Off-the-shelf AI SRE agents assume SaaS monitoring, GitHub and cloud connectivity. Firms on self-hosted GitLab, Prometheus and ServiceNow need custom wiring ([GitHub docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)).

### One safety baseline for every Ritru agent

The market has already settled on what "safe" means, so Ritru should adopt it as a fixed house rule and publish it. Agents start read-only. Azure SRE Agent defaults to review mode, where only named administrators approve each action, and Microsoft advises watching for 2–4 weeks before letting specific, always-approved triggers run alone ([Microsoft Learn](https://learn.microsoft.com/azure/sre-agent/run-modes)). Every fix ends in a PR that a human merges. That is how Wiz, Copilot Autofix and Mobb all work ([Wiz](https://wiz.io/blog/securing-software-age-of-agentic-coding); [InfoQ](https://www.infoq.com/news/2026/06/azuredevops-copilot-autofix/); [Pixee](https://www.pixee.ai/blog/best-automated-remediation-tools-2026)). The agent runs in a sandbox with no secrets, can push only to its own branches, and sits behind a deny-by-default network firewall, as GitHub does ([GitHub docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). Access uses short-lived tokens scoped to one repository per session, never "always allow" ([DevClass](https://devclass.com/2025/05/27/researchers-warn-of-prompt-injection-vulnerability-in-github-mcp-with-no-obvious-fix/)). Agent identity can now come from GA products such as Microsoft Entra Agent ID ([Big Hat Group](https://www.bighatgroup.com/blog/entra-agent-id-ga-deep-dive/)).

For Ritru that becomes six rules that apply to every service below. (1) The agent never holds production admin or "apply" credentials. (2) Discovery uses a read-only role. (3) Any change is a plan plus policy checks plus a PR. (4) A named client approver merges, and the client's own pipeline applies. (5) Every run saves an evidence bundle. (6) Ticket text, finding text and repository content are treated as untrusted input that cannot widen the agent's permissions. The Jira-to-PR design in `solutions/jira-to-pr/architecture/ADR-0001-phase-0.md` already encodes most of this: a credential-free sandbox, a separate verifier, a trusted publisher that alone holds write access, and a gate that checks the exact verified code before the PR. That design is the seed of the shared engine. What buyers trust today forms a simple ladder. Rung 1 is read-only summaries. Rung 2 is verdicts with evidence that a human approves. Rung 3 is agent-drafted PRs that a human merges. Pre-approved, reversible containment is a later rung. Fully autonomous production change is not accepted today. The survey data backs this up: **only 26% of organisations use AI to respond to security incidents, and 33% to investigate them** ([SANS 2025 AI Survey](https://www.sans.org/white-papers/sans-2025-ai-survey-measuring-ai-impact-security-three-years-later)). Ritru should sell rungs 1 to 3 only.

## The landing zone agent survives, but in narrower form

The idea as first evaluated was this. An agent gathers requirements, writes a decision record, generates configs for AWS Control Tower and LZA, Azure Landing Zones on AVM and GCP Fabric FAST, runs policy checks and a plan, opens a PR, and later reports drift. The design is still right. It matches current best practice almost exactly. AWS keeps deployment inside the LZA pipeline and gives its MCP server temporary credentials only ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/03/new-lza-mcp-server-ai-assisted)). Microsoft's migration agent produces configs "ready for deployment workflows" and stops there ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/migrate/azure-copilot-migration-agent?view=migrate)). Practitioners who build Terraform agents report hallucinated and duplicated code as the main early problem, and they rely on human sign-off before merge ([Rackspace](https://www.rackspace.com/blog/building-terraform-ai-agent-automating-cloud-infrastructure-with-ai)). Ritru's plan-and-PR design answers that directly.

The market around the idea has moved, though, in three ways. The first change cuts against it: **generating a single-cloud landing zone is now free**. The Azure migration agent outputs platform landing zone Terraform. AWS ships an LZA MCP Server. Google's Application Design Center turns plain language into Terraform built from pre-approved templates ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/migrate/azure-copilot-migration-agent?view=migrate); [GitHub awslabs/lza-mcp-server](https://github.com/awslabs/lza-mcp-server); [Google Cloud](https://cloud.google.com/blog/products/application-development/gemini-cloud-assist-at-next26)). Ritru cannot charge for that step alone. The second change works in its favour: a forced migration has appeared. Microsoft deprecated the classic `caf-enterprise-scale` Terraform module. It gets no updates, its registry notice set archiving for 1 August 2026, and Microsoft "strongly recommends" moving to AVM ([GitHub](https://github.com/Azure/terraform-azurerm-caf-enterprise-scale); [Microsoft](https://techcommunity.microsoft.com/blog/azuretoolsblog/terraform-azure-verified-modules-for-platform-landing-zone-alz-migration-guidanc/4432035)). Any team still on it is now running an unmaintained module. The move depends heavily on Terraform state, which is exactly where a plan-only, PR-based agent helps. Microsoft's own tooling leaves custom resources to the customer. The third change is also in its favour: there is steady demand for new landing zones. **86% of firms are shrinking VMware, but only 4% have finished**, and about three-quarters of those who migrate go to public cloud ([Channel Dive](https://www.channeldive.com/news/broadcom-vmware-migrations-costs-cloudbolt-report/812735/); [Everywan](https://everywan.com/en/blog/vmware-broadcom-two-years-later-the-exodus-that-wasnt)).

The verdict is to keep the agent, re-scope it, and rank it third rather than first. "Multi-cloud landing zone generator" should stop being the headline, because the hyperscalers have made generation free. The new name is the **Landing Zone Upgrade and Drift agent**. It works on existing estates and leads with three things: CAF-to-AVM migration on Azure, LZA config changes on AWS (using the LZA MCP Server as a tool instead of competing with it), and a monthly drift report. Fabric FAST support should wait until a paying client asks. The research found no AI tooling for FAST, but it also found no evidence of demand. Multi-cloud parity stays as a selling point for the minority of clients that run two clouds. It is not the reason anyone buys. Two facts hold the ranking down. No one has counted how many teams still run the classic CAF module. And the research found no data on the size of the landing zone services market or on typical prices. The buyer pool is also narrow, because only about 28% of organisations have a dedicated platform team ([bex.co](https://bex.co/blog/2026/07/10/cncf-platform-engineering-ai-native)). The agent is still worth building third. It shares about 80% of its engine with the top-ranked service, so it costs little extra once that engine exists.

### 1. Cloud fix-to-PR agent

| Field | Detail |
|---|---|
| Problem | Scanners such as Wiz, Defender for Cloud and AWS Security Hub find cloud misconfigurations every day. The fix must go into the IaC module that created the resource, or the next deploy brings the problem back. Finding the owning repo and module and writing a safe change is slow, manual work, so backlogs grow |
| Buyer | Head of cloud security or CISO pays. The platform team lead is the day-to-day champion, because the PRs land in their repos |
| Agent design | (1) Read new findings through a read-only scanner API or MCP server (Wiz MCP, Security Hub). (2) Map each resource to its repo and module using tags and state. (3) In a sandbox, write the smallest change that fixes it. (4) Run plan, policy checks and tests. (5) The trusted publisher opens a PR with the finding, the plan diff and the policy results. (6) After merge and apply by the client's pipeline, re-scan to confirm the finding is closed. Start only with "safe classes": turn on encryption, block public access, enable logging, add required tags |
| Guardrails | Read-only scanner access. No cloud write credentials anywhere in the agent. Repo writes only through the publisher, only to an agent branch prefix. One repo per run. Finding text treated as untrusted. Human merge required. Logic-heavy fixes stay out of scope at first: an independent test found only **65% accuracy on access-control fixes, against 87% on simpler sanitizer fixes** ([Safeguard](https://safeguard.sh/resources/blog/snyk-agent-fix-autofix-field-test-2026)) |
| Competition | Wiz Green Agent and Wiz MCP for Wiz-only shops ([Wiz](https://wiz.io/blog/securing-software-age-of-agentic-coding)). Copilot Autofix and Snyk Agent Fix for application code ([InfoQ](https://www.infoq.com/news/2026/06/azuredevops-copilot-autofix/)). Mobb. Ritru's angle: works with any scanner, the client's own module layout and the client's own CI gates |

### Services to avoid

Six ideas fail the test, and Ritru should say no to them clearly. The first is a stand-alone AI SOC triage product. Rivals have raised $166M–$200M, and Microsoft gives triage away inside E5. The second is any autonomous remediation or "self-healing" offer, which Gartner names as the place AI projects fail ([The Register](https://www.theregister.com/software/2026/04/07/only-28-of-ai-infrastructure-projects-fully-pay-off/5221652)). The third is a generic ticket-to-PR coding agent sold as a product. Free and $10-a-month tools already do this, so Ritru's Jira-to-PR work is an engine and a showcase, not something to sell on its own. The fourth is FinOps commitment buying, where ProsperOps and nOps take 20–35% of savings on mature platforms ([usage.ai](https://www.usage.ai/blogs/finops/tools/best-ai-agents-for-finops/)). The fifth is VMware or mainframe migration *planning* agents, which AWS gives away. The sixth is phishing triage in E5 tenants, where the GA agent is effectively free ([Microsoft Defender docs](https://learn.microsoft.com/en-us/defender-xdr/security-alert-triage-agent)).

## One change engine powers the first three offers

The three services to start with are the readiness review (rank 2), the cloud fix-to-PR agent (rank 1) and the landing zone upgrade and drift agent (rank 3). Sell the review from week one, because it needs almost no build and every later sale starts with it. Build fix-to-PR first, because it has the biggest budget and repeat revenue. Build the landing zone upgrade agent third, because it reuses the same engine and the founder's existing design. Fix-to-PR and the landing zone agent share most of their parts. Both need read-only discovery, a credential-free sandbox, Terraform plan and policy checks, a trusted publisher, an evidence bundle and a merge tracker. The Kubernetes upgrade agent (rank 6) is a third "recipe" for that same engine in quarter two. One caution for the engine: the Jira-to-PR draft uses OpenAI's Agents API, which its own documentation lists as US-only for data residency with no zero-data-retention option ([OpenAI](https://developers.openai.com/api/docs/guides/agents-api/overview)). EU clients will ask about that. Keep the engine model-neutral, so the agent layer can switch to Claude, Azure-hosted or in-region models without changing the safety design.

### A five-step pricing and packaging ladder

Benchmarks for small agent firms are thin and mostly self-reported, so treat the ranges below as starting points to test, not market facts. The anchors come from three places. Boutique pilots commonly run 4–6 weeks at **$25K–$60K fixed fee, with the success metric agreed in writing first** ([Strataigize](https://www.strataigize.com/insights/how-much-do-ai-agents-cost/)). A survey of 250 agencies puts the median run cost per agent at **$1,800 a month, with the top quarter at $4,200** ([Digital Applied](https://www.digitalapplied.com/blog/agentic-ai-adoption-survey-2026-250-agencies)). Outcome units in other markets sit around $0.99–$2 per resolution and are falling fast ([Channel Dive](https://www.channeldive.com/news/agentic-ai-outcome-pricing-models-zendesk-gartner/829209/)).

| Step | What the client gets | Suggested price (to validate) | Purpose |
|---|---|---|---|
| 0. Open blueprints | Public designs, the safety baseline, checklists, demo repos | Free | Proof of skill and lead source |
| 1. Readiness review | 2–3 week review, inventory, risk map, fix plan | $12K–$25K fixed | Low-risk first purchase |
| 2. Proof-of-value pilot | 4–6 weeks, one repo or one landing zone area, shadow or PR-only mode, written success metric | $25K–$50K fixed | Prove results on the client's own data |
| 3. Production build | Hardened agent wired to the client's CI, identity and ticketing; evidence bundle; runbook | $30K–$80K fixed, by scope | Turn the pilot into a running system |
| 4. Run retainer | Monitoring, evals, cost scorecard, drift reports, monthly tuning | $2K–$5K per agent per month, plus pass-through costs | Repeat revenue |
| 5. Outcome bonus (optional) | Payment per merged fix or closed finding above an agreed baseline, capped | Small share of fees, capped | Shares upside without cash-flow risk |

Three packaging rules matter. Keep the at-risk share small. Fin's per-outcome pricing taught buyers that costs rise as success rises, and they complain about it ([Gleap](https://www.gleap.ai/blog/intercom-fin-ai-pricing-2026)). Define every outcome unit in the contract, so the count cannot be disputed ([Flexprice](https://flexprice.io/blog/why-ai-companies-have-adopted-usage-based-pricing)). And use hyperscaler money to fund the pilot step. AWS offers $50K in marketing funds for the AI Specialization plus $25K for an Agentic category validation, and it runs per-project proof-of-concept funding ([AWS APN](https://aws.amazon.com/blogs/apn/powering-partner-success-2026-innovations/)). Google has a $750M partner fund for agent prototypes ([Google Cloud](https://www.googlecloudpresscorner.com/2026-04-22-Google-Cloud-Commits-750-Million-to-Accelerate-Partners-Agentic-AI-Development)). Marketplaces keep only about 3% on standard listings, and clients can pay from committed cloud spend ([Instantdm](https://instantdm.com/blog/best-ai-agent-marketplaces-2026)). The trade-off is lock-in. Keep the blueprints portable, and offer cloud-specific funded delivery tracks.

| Days | Build | Sell | Proof by the end |
|---|---|---|---|
| 1–30 | Publish the six-rule safety baseline and the readiness checklist mapped to the OWASP Agentic Top 10. Turn the Jira-to-PR design into the shared engine skeleton: sandbox with no credentials, verifier, trusted publisher, evidence bundle | Line up 3 design-partner readiness reviews. Start the AWS partner validation and a Google partner fund application | 2 reviews signed. Engine opens a dry-run PR on a demo Terraform repo |
| 31–60 | Fix-to-PR version 0.1 on a demo estate with deliberate misconfigurations, covering safe fix classes only. Start the AVM migration recipe on a sandbox Azure tenant running the classic CAF module | Convert one review into a paid fix-to-PR pilot. Publish a short, plain write-up of the CAF-to-AVM risk | 1 paid pilot running in PR-only mode. Merge rate and revert count tracked |
| 61–90 | Harden fix-to-PR for the pilot client. Finish the AVM recipe with zero-unplanned-destroy checks and a drift report | Propose a run retainer to the pilot client. Pitch the landing zone upgrade to 5 Azure-heavy prospects. Prepare a marketplace listing | First retainer signed or a clear reason why not. First landing zone pilot booked. Honest case study published |

Decide at day 90 with simple tests. Continue fix-to-PR if pilot PRs merge at **70% or better**. For comparison, human PRs merge at about 82.6% and agent PRs at 55–86% in open-source data ([arXiv 2602.04226](https://arxiv.org/html/2602.04226v1)). Fix-to-PR must also have made zero unapproved changes, and the client must be willing to pay monthly. Continue the landing zone agent only if at least one prospect confirms an unfinished CAF-to-AVM migration or LZA backlog. Keep the readiness review either way, because it is the source of leads for every other offer. Every number in client material should be re-checked against the vendor's own page. Many of the prices in this report come from third-party guides, because primary pages could not be fetched during research.

## Conclusion

Over the past year the vendors have turned "write an agent that does X" into a free feature, so that is no longer the opportunity. What clients still pay for is proof that an agent's change is safe, correct and approved. That proof is mostly made of plumbing: read-only roles, plan diffs, policy checks, named approvers, evidence bundles and honest scorecards. The vendors under-build this part because it differs for every client. Ritru's open-blueprint habit turns that into an advantage. A published safety baseline and a shared PR engine are credible because anyone can inspect them, and that matters in a market where Gartner thinks only about 130 of the thousands of "agentic" vendors are real ([Gartner](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027)).

The landing zone reassessment shows the wider lesson. The original design was sound, but its headline feature, multi-cloud generation, is the one part that has become free. Its lasting value sits in the unglamorous parts: brownfield adoption, forced migrations, drift and evidence. Ritru should expect the same shift to repeat. Whatever an agent can generate today will be bundled by a hyperscaler within a year. The safe, approved delivery of that output into a real client estate stays custom work, and that is the business to build.
